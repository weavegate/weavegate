# RG001: invariant violated under a controlled schedule

`RG001` means a declared SQL assertion returned violating evidence under a
controlled release schedule.

```text
## weavegate: FAIL (RG001)
scenario: concurrent-assign | schedules explored: 1 | violating: sch_7dcb74b1e506
assertion: active-assignment-is-unique
flaky: false (repeat=20)
replay: weavegate run --config fixtures/matching-slice/.weavegate/config.yaml --scenario concurrent-assign --variant vulnerable --replay sch_7dcb74b1e506 --repeat 20

error[RG001]: invariant violated under a controlled schedule
  observed:  active-assignment-is-unique returned 1 row: active_assignment_count=2 project_request_id=42
  assertion: active-assignment-is-unique
  invariant: a declared state invariant must hold under every release schedule the database permits
  reason:    commonly a read-then-write path without a lock or a unique constraint
  help:      add a unique constraint on the contested key
             take a pessimistic lock (SELECT ... FOR UPDATE) before insert
             use an idempotency key on the write
  evidence:  schedule sch_7dcb74b1e506 · trace.json · 1 violating row
```

## What this means

The named assertion did not hold after weavegate executed the displayed
schedule. The `observed` line is a deterministic rendering of the rows returned
by that assertion. The `evidence` line identifies the saved schedule and trace
that support the verdict.

## When it fires

`RG001` fires when a configured SQL assertion reports a violation after a
controlled schedule. The code is derived from the assertion Oracle's violation
kind; it is not selected in configuration.

## Why it happens

A common cause is a read-check-write path in which two transactions both pass
the check before either write becomes visible to the other. Without database
serialization at the contested key, both writes can commit and break the
declared invariant.

## How to fix it

Choose a database-enforced serialization mechanism that matches the workflow:

- add an appropriate unique constraint and handle the losing write explicitly;
- take a pessimistic lock, such as `SELECT ... FOR UPDATE`, before deciding to
  insert; or
- attach an idempotency key to the write and make retries converge.

The fixture in this repository has measured the `SELECT ... FOR UPDATE` path.
The PASS semantics for a unique-constraint path are defined, but that path has
not yet been measured by the committed fixture.

Replay the saved schedule after the change. A stable PASS shows that this
schedule no longer produces this assertion violation.

## What this code does not claim

`RG001` does not claim that the workflow has no other race, or that a PASS is a
proof over every possible database execution. See
[PASS is not a proof](../exit-codes.md#pass-is-not-a-proof).

All SQL assertion violations currently map to `RG001`, regardless of the more
specific anomaly an assertion may be detecting. More specific codes such as
RG002 or RG003 require an Oracle with structural knowledge of the anomaly,
such as a future differential Oracle.

One RG001 block shows one representative evidence set. When the same assertion
has additional sets, the evidence line points to their complete list in
`observation.json`.

When a scenario declares multiple assertions, the single saved `trace.json`
does not claim to correspond to every diagnostic produced by different runs.
