# RG090: determinism check failed

`RG090` means repeated executions of one saved schedule did not produce one
normalized result.

```text
## weavegate: FLAKY (RG090)
scenario: concurrent-assign | schedules explored: 1 | violating: sch_ba00582f9632
flaky: true (repeat=20)
replay: weavegate run --config fixtures/matching-slice/.weavegate/config.yaml --scenario concurrent-assign --variant vulnerable --replay sch_ba00582f9632 --repeat 20

error[RG090]: determinism check failed
  observed:  repeated executions produced more than one normalized fingerprint
  invariant: repeated executions of the same schedule must produce the same normalized result
  reason:    replays diverged in normalized terminal state or timing classification
  help:      compare the replay fingerprints and their counts
             check arrive_timeout_ms against the environment's scheduling behavior
  evidence:  schedule sch_ba00582f9632 · trace.json · 0 violating rows
```

## What this means

Weavegate audits whether it can reproduce its own result. For this run, the
same schedule produced different normalized fingerprints across repeats, so
the tool refused to report either a clean pass or a stable violation. The
process exits 3.

## When it fires

`RG090` fires when repeated execution of the same schedule diverges, or when an
exploration discovery and its replay do not have the same normalized
fingerprint. This is an engine-derived signal rather than an Oracle violation.

## Why it happens

The fingerprint includes normalized worker terminal states and timing
classifications. It can diverge when a worker sometimes completes and
sometimes times out or is classified as database-blocked under the effective
deadline.

## How to fix it

- Compare `observation.fingerprints` and their counts to see how many normalized
  outcomes occurred.
- Inspect `trace.json` for the terminal or timing classification that changed.
- Check whether `run.arrive_timeout_ms` is appropriate for the execution
  environment without using sleep as a coordination mechanism.
- Re-run with the same schedule and enough repeats to establish whether the
  divergence remains.

## What this code does not claim

`RG090` does not identify an application invariant violation and does not say
which replay outcome is correct. It says weavegate could not reproduce one
stable normalized result, so a PASS or violation judgment would be unsafe.
It also does not prove that increasing a timeout fixes the workflow; weakening
a check can conceal the signal instead of removing its cause.
